# DEVELOPER.md 撰寫規範

> 本規範規定 `DEVELOPER.md` **該寫什麼、怎麼寫**，以及它與其他文件、與 Claude 技能怎麼分工。
> 不規定專案的技術選型。通用規範，任何專案皆適用。

---

## 1. 目的與適用範圍

### 1.1 目的

讓一個**沒碰過這個專案的開發者**——人或 AI agent——照著文件從零把環境架起來、跑得動、改得動、驗證得了、交得出去，過程中不需要問任何人。

「沒碰過這個專案的開發者」包含**半年後的你自己**，也包含**每一次新開的 agent 工作階段**。

### 1.2 讀者

讀者是**要修改這個專案的人與 agent**，不是使用它的人。可以假設對方會用 git、會用終端機，但**不可**假設對方知道這個專案的任何約定。

### 1.3 文件地圖

每份文件只回答一個問題。`DEVELOPER.md` 是「改它」的入口，其他問題**連結**過去，不複述。

根目錄**只**放 `README.md`、`CLAUDE.md`、`LICENSE` 三個檔——它們的位置由 GitHub 與 Claude Code 決定，搬走就失效。其餘文件**一律**放在 `docs/`。

| 位置 | 回答的問題 | 由誰維護 | 規範 |
| :--- | :--- | :--- | :--- |
| `README.md` | 怎麼用它 | 人工 | `README_RULES.md` |
| `LICENSE` | 我能拿它做什麼 | 人工 | `README_RULES.md` §4.11 |
| `CLAUDE.md` | agent 開工前要知道什麼、去哪找 | 人工＋`setup-matt-pocock-skills` | 本規範 §4.9 |
| `docs/PRODUCT.md` | 為誰做、為什麼做 | impeccable `init` | `PRODUCT_RULES.md` |
| `docs/DESIGN.md` | 使用者介面長什麼樣、怎麼互動 | impeccable `document` | `DESIGN_RULES.md` |
| **`docs/DEVELOPER.md`** | **怎麼改它** | **人工** | **本規範** |
| `docs/GLOSSARY.md` | 名詞是什麼意思 | `domain-modeling` | `GLOSSARY_RULES.md` |
| `docs/adr/` | 為什麼這樣決定 | `domain-modeling` | 技能的 ADR 格式（§4.8） |
| `docs/CHANGELOG.md` | 每一版變了什麼 | 人工或進版腳本 | `CHANGELOG_RULES.md` |
| `docs/DEPLOY.md` | 部署型專案在各主機上怎麼架 | 人工 | `README_RULES.md` §4.10 |
| `docs/agents/` | agent 的工作設定（issue tracker、triage 標籤、領域文件位置） | `setup-matt-pocock-skills` | 技能自帶 |
| `docs/rules/` | 文件與發佈規範的副本 | 從正典複製 | — |

規範沒有管到的文件（路線圖、操作手冊、逆向筆記、待解問題）也放 `docs/`，以內容命名。

條文中提到其他文件時只寫檔名（「見 `CHANGELOG.md`」），實際位置以本表為準。

由技能維護的文件，**建議**用該技能產生與更新；人工修改時**必須**維持技能要求的檔名、章名與格式，否則技能讀不到。

### 1.4 本規範不管什麼

- 不管程式碼風格細節（縮排、命名）——那由各專案的 linter 設定決定，本文件只需指出設定檔在哪。
- 不管發佈流程 → `RELEASE_RULES.md`
- 不管版本號語意 → `VERSION_RULES.md`
- 不管名詞表怎麼寫 → `GLOSSARY_RULES.md`；ADR 的格式以 `domain-modeling` 技能為準（§4.8）

### 1.5 強制語彙

| 用詞 | 意義 |
| :--- | :--- |
| **必須** | 不做就是不合規（MUST） |
| **建議** | 有更好的理由才可以不做（SHOULD） |
| **可** | 自行斟酌（MAY） |

## 2. 檔案位置與命名

- 檔名**必須**為 `DEVELOPER.md`，**必須**放在 `docs/`。
- H1 **必須**為「《<專案名稱>》(<專案代號>) 開發者文件」。
- 編碼**必須**為 **UTF-8 無 BOM**，換行**必須**為 **LF**，檔尾**必須**留一個換行。
- 語言**必須**為**繁體中文**；指令、檔名、型別名、API 名稱保留原文。
- 單節過長時**可**外拆成 `docs/` 下的另一份文件，但必要章節的標題與摘要**必須**留在 `DEVELOPER.md`。

## 3. 結構：必要章節 / 選用章節

### 3.1 必要章節（依此順序）

順序即新人的實際動線：裝環境 → 跑起來 → 看懂 → 改 → 驗證 → 交出去。

| # | 章節 | 必須回答的問題 |
| :-: | :--- | :--- |
| 1 | 技術棧與系統需求 | 用什麼寫的？需要哪些工具、哪個版本？ |
| 2 | 環境建置 | 從乾淨的機器到能跑，要做哪幾步？ |
| 3 | 日常開發 | 怎麼啟動？怎麼熱更新？怎麼除錯？ |
| 4 | 目錄結構 | 東西放哪？我要改的檔在哪？其他文件在哪？ |
| 5 | 架構與關鍵設計決策 | 有哪些模組、各自的介面與接縫？為什麼這樣切？哪些決定不能隨便推翻？ |
| 6 | 測試 | 怎麼跑？在哪些接縫上測？哪些會被略過？為什麼？ |
| 7 | 建置與產物 | 怎麼建？產出什麼？**版本號要同步改哪幾處？** |
| 8 | 分支、commit 與 PR 慣例 | 從哪開分支？訊息怎麼寫？舊版怎麼保留？ |
| 9 | 安全與敏感資料 | 什麼絕對不能進版控？權限開到哪？ |
| 10 | 已知陷阱 | 前人踩過哪些坑？ |

沒有內容的必要章節**必須**保留標題並註明現況（例如「目前無」），**不得**刪除。

### 3.2 選用章節

- CI / 自動化
- 資源、資料檔的產生工具
- 效能量測方式
- 對外相依服務與帳號申請流程

## 4. 撰寫規則

### 4.1 各必要章節的最低要求

**§1 技術棧與系統需求**
**必須**列出語言／執行期／建置工具及其**版本或最低版本**，以及作業系統限制。**禁止**只寫「Node」不寫版本。

**§2 環境建置**
**必須**是可逐步照做的編號步驟，從取得原始碼開始。每一步**必須**有可觀察的完成狀態（看到什麼輸出、產生什麼檔案）。

**§3 日常開發**
**必須**包含啟動指令、修改後如何反映、如何看到錯誤訊息（log 位置、除錯開關）。

**§4 目錄結構**
**必須**用樹狀圖列到「有意義的那一層」為止，每個項目**必須**有一句話說明職責。**禁止**貼出完整檔案清單，也**禁止**列出 `node_modules`、`target`、`dist` 等產生物。
樹狀圖**必須**列出 §1.3 文件地圖中本專案實際有的文件，各附一句職責——這是人與 agent 找到它們的地方。

**§5 架構與關鍵設計決策**
見 §4.7。

**§6 測試**
**必須**寫出跑測試的指令、測試分類（單元／整合／回歸），以及已約定的接縫表（見 §4.11）。若有測試會因缺少外部檔案而被略過，**必須**說明：略過的條件、檔案該放哪、如何辨識「略過」與「失敗」。

**§7 建置與產物**
**必須**寫出建置指令與**每一個產物的名稱與用途**。
**必須**包含「版本號同步清單」（見 §4.2）。

**§8 分支、commit 與 PR 慣例**
**必須**寫明主要分支名稱、從哪開分支、commit 訊息格式。
**必須**包含**舊實作的保留規則**（見 §4.3）。

**§9 安全與敏感資料**
見 §4.4。

**§10 已知陷阱**
見 §4.5。

### 4.2 版本號同步清單（§7 必備）

版本號通常同時存在於多個檔案，不同步就會出現「安裝檔寫 v1.0.1、關於視窗寫 v1.0.0」。

**必須**在 §7 明確宣告：

1. **單一來源**——哪一個檔案的版本號是準的。
2. **同步清單**——所有需要跟著改的位置，逐一列出檔案與欄位。
3. 能由建置流程**自動衍生**的位置**必須**標明「自動」，並**禁止**手動修改。

範例（虛構專案 `MYAPP`）：

```markdown
### 版本號

單一來源：`package.json` 的 `version`

| 位置 | 欄位 | 方式 |
| :--- | :--- | :--- |
| `package.json` | `version` | 手動（單一來源） |
| `src-tauri/tauri.conf.json` | `version` | 手動 |
| `src-tauri/Cargo.toml` | `package.version` | 手動 |
| 產物檔名 | — | 自動（由建置腳本讀取單一來源） |
```

**不需要**撰寫自動改版本號的腳本；一致性由 `RELEASE_RULES.md` 的發佈檢查清單逐項核對。專案**可**提供**唯讀**的檢查指令（把各處版本號印出來比對），但非必要。

### 4.3 舊實作的保留規則（§8 必備）

當一次改版使**舊實作無法與新實作共存於主分支**時（技術棧更替、整體重寫）：

- 舊實作**必須**以分支保留，**禁止**直接刪除。
- 分支名稱**建議**用 `legacy/<簡短描述>`，並在 §8 記錄「這個分支是什麼、為什麼留、留到什麼時候」。
- 該分支**不再接受新功能**；僅在有明確理由時接受修正。
- 主分支（`main`）走新實作。
- 若舊實作是驗證新實作正確性的基準（oracle），**必須**在 §8 寫明驗證方式與解除保留的條件。

`VERSION_RULES.md`（MAJOR 節）與 `RELEASE_RULES.md`（舊版本處置節）交叉引用本條，實質規則以本條為準。

### 4.4 安全與敏感資料（§9 必備）

**必須**涵蓋且**只**涵蓋以下四項。編碼層次的安全（輸入驗證、注入防護等）不在本規範範圍。

| # | 項目 | 必須寫明 |
| :-: | :--- | :--- |
| 1 | 機密不進版控 | 哪些檔案／欄位是機密（金鑰、受信任的憑證、密碼、個人路徑、帳號），如何排除（`.gitignore` 條目），以及開發者本機該把它們放哪；未被任何地方信任的自簽簽章憑證不算機密，進了版控就註明這一點（見 `RELEASE_RULES.md` §4.2） |
| 2 | 權限最小化 | 程式向作業系統／執行期要求了哪些權限（檔案存取範圍、網路、系統 API），為什麼需要，以及刻意**不要**的權限 |
| 3 | 依賴來源與鎖檔 | 鎖檔（`package-lock.json`、`Cargo.lock` 等）是否進版控，安裝時用哪個指令（例如 `npm ci` 而非 `npm install`），第三方資源的來源 |
| 4 | 破壞性操作的保護 | 程式會覆寫或刪除使用者資料的地方，以及可回復機制（備份策略、是否覆蓋既有備份、如何還原） |

簽章、SmartScreen、產物校驗碼屬於**發佈**議題，寫在 `RELEASE_RULES.md`，不寫在此。

### 4.5 已知陷阱（§10 必備）

記錄開發過程中實際踩到、且**下一個人很可能再踩一次**的問題。

每一條**必須**用固定三段式：

```markdown
#### <一句話標題>

- **症狀**：你會看到什麼（錯誤訊息原文、異常行為）
- **原因**：為什麼會這樣
- **處置**：怎麼解決或怎麼避開
```

規則：

- 症狀**必須**寫實際可搜尋的字串（錯誤訊息原文），這是別人找到這一條的唯一途徑。
- **禁止**只寫「要注意 X」這種事後看不懂的句子。
- **踩到就補一條**——排除一個非顯而易見的問題後，在合併前補進本節。
- 陷阱若已被修掉且不會再發生，**必須**刪除該條，並在 `CHANGELOG.md` 記錄。
- 尚未踩到任何坑時，保留章節標題並寫「目前無」。

範例：

```markdown
#### 安裝完工具鏈後，已開著的終端機仍找不到指令

- **症狀**：執行建置指令時出現 `cargo: command not found`，但工具鏈確實已安裝完成
- **原因**：安裝程式只更新了系統的 PATH，不會影響已經開著的終端機工作階段
- **處置**：重開終端機；或讓建置腳本自行到預設安裝路徑尋找執行檔
```

### 4.6 一般撰寫規則

- 全文**只有一個** H1；必要章節用 H2。
- 程式碼區塊**必須**標註語言，指令**禁止**帶提示符。
- 庫內連結**必須**用相對路徑。
- 說明「為什麼」重於「是什麼」——指令本身看得懂，理由看不懂。
- 同一件事只寫在一個地方：名詞在 `GLOSSARY.md`、決策理由在 ADR、產品事實在 `PRODUCT.md`、視覺在 `DESIGN.md`。`DEVELOPER.md` 連結過去。

### 4.7 架構與關鍵設計決策（§5 必備）

**模組職責**

**必須**用深模組的語彙（§4.10）列出主要模組：每個模組的職責、介面、接縫與轉接器，以及**依賴方向**。模組名稱與領域名詞**必須**用 `GLOSSARY.md` 的用詞；表上沒有的詞，先補進 `GLOSSARY.md` 再用。

**模組介面**

模組之間、程式與外界之間的契約——介面、輸入協議、存檔格式、事件定義——**必須**寫在 §5 的「模組介面」小節；過長時外拆 `docs/API.md` 並在此留摘要與連結。**禁止**寫進 `DESIGN.md`（那裡只放使用者介面的視覺）。

**領域規格**

遊戲機制、規則清單、計分公式這類「產品怎麼運作」的規格不是每個專案都有。有的話**必須**放在 `docs/` 下以內容命名（例如 `docs/MECHANICS.md`），並從 §5 連結；**禁止**命名為 `DESIGN.md`。

**決策**

每個「刻意這樣做」的決定**必須**記錄**理由**——只寫結論不寫理由，等於沒寫。依下列三個條件分流：

1. **難以反轉**：日後改變心意的代價明顯
2. **沒有脈絡會令人意外**：後來的人看到程式碼會問「為什麼這樣做」
3. **真正的取捨**：有過實際的替代方案，因特定理由選了其中一個

| 情況 | 寫在哪 |
| :--- | :--- |
| 三個條件**全部**成立 | 立 ADR（`docs/adr/`，格式見 §4.8）；§5 只留一行摘要與連結 |
| 不全成立，但理由不明顯 | §5 內用「決定／理由／代價」三段 |
| 理由一看就懂 | 不記錄 |

§5 **禁止**複述 ADR 的內文——同一個理由寫兩處，改一處另一處就過時。

### 4.8 名詞表與 ADR（由 `domain-modeling` 維護）

| 項目 | 規定 |
| :--- | :--- |
| 名詞表 | `docs/GLOSSARY.md`，怎麼寫見 `GLOSSARY_RULES.md`（含從舊 `CONTEXT.md` 遷移的步驟） |
| ADR | `docs/adr/NNNN-<slug>.md`，四位數流水號；一段話講清楚脈絡、決定、理由即可，格式以 `domain-modeling` 技能為準 |
| 建立時機 | 第一個名詞確定時才建名詞表，第一個 ADR 需要時才建 `docs/adr/`；**禁止**預先建空檔 |

### 4.9 `CLAUDE.md` 與 `docs/agents/`

`CLAUDE.md` 是 agent 每一輪都會載入的入口，每一行都佔用它的注意力。因此它只放**指標**與**看程式碼看不出來的約定**：

- `CLAUDE.md` **必須**放在根目錄（Claude Code 只自動載入根目錄那份）；`docs/agents/` 放在 `docs/`。
- **必須**用一行一份的方式指向 §1.3 文件地圖中本專案有的文件，寫出完整路徑與**什麼時候該讀**（「改使用者介面前讀 `docs/DESIGN.md`」）。
- **必須**保留 `setup-matt-pocock-skills` 產生的 `## Agent skills` 段落，並與 `docs/agents/` 的內容一致。
- **可**寫看程式碼查不到的約定（文件語言、提問方式、commit 時要同步做的事），一條一行。
- **禁止**複述 `DEVELOPER.md` 已有的指令、目錄或架構說明——指過去就好。
- 建置與測試指令的正本在 `DEVELOPER.md`；`CLAUDE.md` 若需要列出，**必須**與其一致。

撰寫細節（指標的措辭、正向表述、剪除冗詞）**建議**依 `writing-for-agents` 技能。

### 4.10 模組設計：深模組（§5 必備）

程式**必須**以**深模組**組織：介面小、背後行為多，放在乾淨的接縫上，並且能穿過介面測試。用語以 `codebase-design` 技能為準：

| 用詞 | 意思 |
| :--- | :--- |
| 模組 | 任何有介面與實作的單位：函式、類別、套件都算 |
| 介面 | 呼叫端正確使用模組所需知道的**一切**：型別簽名，加上不變量、呼叫順序、錯誤情形、必要設定 |
| 深度 | 呼叫端每學一點介面，能用到多少行為；**不是**行數 |
| 接縫 | 不必改該處就能替換行為的位置，也就是介面所在之處 |
| 轉接器 | 在接縫上實作介面的具體東西（正式環境的資料庫存取、測試用的記憶體替身） |

規則：

- **深度看槓桿，不看行數。** 本規範**不設**檔案或函式的行數上限；用「實作行數÷介面行數」衡量深度會獎勵灌水，**禁止**這樣評估。判斷一個模組夠不夠深，問三件事：方法能不能更少？參數能不能更簡單？能不能把更多複雜度藏進去？
- **刪除測試。** 想像把這個模組刪掉：複雜度跟著消失，代表它只是一層轉發，**必須**合併或刪除；複雜度散回 N 個呼叫端，代表它值得存在。**禁止**保留只做轉發的空殼模組。
- **只經入口檔。** 外部**必須**只透過模組的入口檔（對外公開的那幾個檔）使用它，**禁止**直接 import 模組內部子資料夾的檔。實作放子資料夾，測試放模組自己的 `tests/`。**建議**用多個小入口檔，**禁止**用一個把整棵子樹重新匯出的總匯出檔（barrel）。
- **依賴不得循環。** 模組之間的依賴**必須**是單向的，並在 §5 寫明方向。TypeScript 專案**建議**用 `setup-ts-deep-modules` 技能裝 dependency-cruiser 自動檢查；其他語言**可**用對應工具或在 code review 檢查。
- **一個轉接器是假設，兩個才是真接縫。** **禁止**為只有一種實作的東西另開接縫；至少要有正式與測試兩種轉接器才值得。
- **接受依賴，不自己建立；回傳結果，不偷偷改狀態。** 這兩點讓模組能在接縫上測試。

§5 的模組表**必須**有「介面」與「接縫／轉接器」兩欄。想改模組形狀時，**建議**依 `codebase-design` 技能的 DEEPENING 與 DESIGN-IT-TWICE 流程評估。

### 4.11 測試（§6 必備）

測試的做法以 `tdd` 技能為準：

**測試先行**

- **修 bug 必須**先寫一個重現它、目前會失敗的測試，再修到它通過。
- 純邏輯（沒有 I/O）的模組**必須**測試先行。
- 使用者介面、建置與部署腳本、一次性工具**建議**測試先行。
- 迴圈是**先紅後綠**：先寫一個失敗的測試，再寫剛好讓它通過的程式；**一次一片**（一個接縫、一個測試、一段最小實作），每片都依上一片學到的調整。**禁止**先寫完全部測試再寫實作。
- 重構不在紅綠迴圈裡，留到 review 階段。

**只在約定的接縫上測**

- 測試**必須**穿過模組的介面，**禁止** import 模組內部、mock 內部協作者、測私有函式、或繞過介面直接查資料庫驗證。判準：重構時行為沒變、測試卻壞了，就是測錯了地方。
- 寫測試前**必須**先約定要測的接縫。§6 **必須**有一張接縫表，`tdd` 技能開工前會讀它：

```markdown
| 接縫 | 抓得到 | 抓不到 |
| :--- | :--- | :--- |
| `core` 的 `applyAction()` | 規則清單裡每一條的結果 | 畫面是否正確顯示 |
```

- 深化模組後，淺模組上的舊測試**必須**刪除，改在新介面上測——取代，不疊加。
- 只有真正在外部、不受你控制的服務才 mock；自己的服務用記憶體轉接器，有本機替身（例如記憶體資料庫）的用替身。

**期望值要有獨立來源**

**禁止**套套邏輯的測試：期望值用與程式相同的算法重算（`expect(add(a, b)).toBe(a + b)`）、或把常數斷言等於自己，永遠不會失敗。期望值**必須**來自獨立的事實：已知正確的字面值、手算的實例、規格本身。
