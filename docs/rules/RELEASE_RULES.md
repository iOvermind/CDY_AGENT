# 發佈規範

> 本規範規定**發佈時產出什麼、怎麼命名、怎麼驗證、怎麼公開**，以及部署型專案每次部署要做什麼。
> 通用規範，任何專案皆適用。

---

## 1. 目的與適用範圍

### 1.1 目的

讓使用者拿到的每一個檔案，都能一眼看出「是哪個專案、哪一版、哪種形式」，並且能自行驗證它沒有被掉包；讓線上跑的每一個服務，都查得到是哪一版。

### 1.2 適用對象

本規範**規範流程，不規範任何一份文件**。專案**不需要**建立 `RELEASE.md`。

專案依交付方式分兩型，各自的流程見 §3：

| 型 | 使用者怎麼拿到 | 例子 |
| :--- | :--- | :--- |
| **發佈型** | 從 GitHub Release 下載產物 | 桌面程式、修改器、可開機映像 |
| **部署型** | 擁有者把服務架在自己的主機上，使用者透過瀏覽器使用 | 自架網站、後台服務 |

兩者都有時（例如同時提供下載版與自架版），兩套流程都要走。

### 1.3 本規範不管什麼

- 不管版本號怎麼訂 → `VERSION_RULES.md`
- 不管變更紀錄怎麼寫 → `CHANGELOG_RULES.md`
- 不管**要出哪些形式的產物**——由各專案在 `DEVELOPER.md` §7「建置與產物」明列（見 §3.1）
- 不管各主機怎麼架 → 專案的 `DEPLOY.md`

### 1.4 強制語彙

| 用詞 | 意義 |
| :--- | :--- |
| **必須** | 不做就是不合規（MUST） |
| **建議** | 有更好的理由才可以不做（SHOULD） |
| **可** | 自行斟酌（MAY） |

## 2. 產物命名與識別

### 2.1 檔名格式

所有對外發佈的產物**必須**依此格式命名：

```text
<專案代號小寫>_v<版本號>_<形式>.<副檔名>
```

| 欄位 | 規則 |
| :--- | :--- |
| `<專案代號小寫>` | 儲存庫名稱轉成小寫（`RICH3_PATCH` → `rich3_patch`） |
| `<版本號>` | 語意化版本號，前面**必須**加 `v` |
| `<形式>` | 產物形式標記，取自 §2.2；**這一版只有一種產物時省略**，連同前面的底線 |

檔名**只能**包含小寫 `a-z`、`0-9`、`.`、`_`、`-`；欄位之間**必須**用底線 `_` 分隔。

> **為什麼把字元限制得這麼死**：GitHub Release 上傳附件時，會把不在
> `A-Za-z0-9.-_` 範圍內的字元一律換成點。中括號、空格都會被改掉——
> `[MYAPP][v1.0.0].exe` 上傳後會變成 `MYAPP.v1.0.0.exe`。
> 本機與線上檔名一旦不同，校驗碼清單就對不上，使用者無從驗證。
> 底線與小寫都在這個字元集內，本機產物與發佈附件才會**逐字相同**；
> 全小寫則讓大小寫不敏感的檔案系統與網址不會出現兩個看似相同的檔。

範例（虛構專案 `MYAPP`）：

```text
myapp_v1.0.0_portable.exe
myapp_v1.0.0_setup.exe
myapp_v1.0.0_sha256sums.txt

只有一種產物時：
myapp_v1.0.0.exe
```

**Docker image** 不是檔案，命名為：

```text
<專案代號小寫>:<版本號>
```

tag **不帶** `v`（Docker 的慣例），例如 `myapp:1.0.0`。**可**另外加上 `latest`，但**必須**同時存在帶版本號的 tag。

### 2.2 形式標記

專案有用到才需要，標記**必須**取自下表，**禁止**自創：

| 標記 | 意義 |
| :--- | :--- |
| `portable` | 免安裝執行檔，解開或直接執行即可 |
| `setup` | 安裝程式 |
| `web` | 網頁版靜態檔封存，解開後可自行架站或直接以瀏覽器開啟 |
| `deploy` | 部署包：compose 檔、設定範例等自架所需檔案 |
| `image` | `docker save` 匯出的 image 封存 |
| `iso` | 可開機映像 |
| `pdf` | 印刷或閱讀用文件 |
| `sha256sums` | 校驗碼清單（§4.3） |

- **不必**每種都出。能出 `portable` 的專案，**必須**以 `portable` 為主要產物：每次發佈都提供，README 的下載表先列它。
- 原始碼封存由 GitHub 自動附上，**不**另行打包。
- 需要新增標記時，**必須**先更新本規範，不得在單一專案臨時發明。

### 2.3 Tag 命名

- git tag **必須**為 `v<版本號>`（`v1.0.0`），**不帶**專案代號與形式標記。
- tag **必須**建立在實際打包或部署所用的那個 commit 上。
- 發佈型與部署型都**必須**打 tag。

## 3. 結構：發佈流程

### 3.1 產物形式由專案決定

本規範**不強制**任何專案出哪幾種形式的產物（§2.2 的 `portable` 優先規則除外）。各專案**必須**在 `DEVELOPER.md` §7「建置與產物」明列自己會產出哪些形式、各自的用途。

一旦列出，**每次發佈都必須全數提供**，**禁止**某一版少出一種。

### 3.2 發佈型的必要步驟（依此順序）

| # | 步驟 | 產出 |
| :-: | :--- | :--- |
| 1 | 確認發佈門檻（§4.1） | — |
| 2 | 更新版本號（依 `VERSION_RULES.md`） | 各設定檔 |
| 3 | 轉換 `CHANGELOG.md` 的 `[Unreleased]` 區塊 | 版本區塊 |
| 4 | 本機打包並檢查產物名稱 | 全部產物 |
| 5 | 簽章（若適用，§4.2） | 已簽章產物 |
| 6 | 產生校驗碼（§4.3） | 校驗碼清單 |
| 7 | 建立並推送 tag | `v<版本號>` |
| 8 | 建立 GitHub Release 頁面（§4.4） | Release |
| 9 | 處置被取代的舊版本（§4.5） | — |

步驟 2、3 **可**由進版腳本一次完成（見 `VERSION_RULES.md` §2.3）。

### 3.3 選用步驟

- 由 CI 自動建置與上傳
- 實機安裝驗證
- 對外公告

### 3.4 部署型的必要步驟（依此順序）

每次部署有面向使用者的變更時：

| # | 步驟 | 產出 |
| :-: | :--- | :--- |
| 1 | 確認 `[Unreleased]` 有內容；空的就只部署、不進版 | — |
| 2 | 更新版本號、轉換 `CHANGELOG.md`（依 `VERSION_RULES.md`，**可**由進版腳本完成） | 版本區塊 |
| 3 | 建置 image，同時標上 `<專案代號小寫>:<版本號>` | image |
| 4 | 建立並推送 tag | `v<版本號>` |
| 5 | 部署到主機，確認線上版本號與 tag 相同 | 線上服務 |

- GitHub Release 頁面與附件**不需要**。若有提供 `deploy` 或 `image` 形式的下載，就依 §3.2 建 Release。
- 線上服務**建議**在頁面某處（頁尾、關於、`/version`）顯示版本號，才查得到跑的是哪一版。

## 4. 執行規則

### 4.1 發佈門檻

以下全部成立才可發佈：

- [ ] 所有預計發佈的變更均已合併至主分支
- [ ] 建置成功，基本功能實測通過
- [ ] `CHANGELOG.md` 已完成 `[Unreleased]` 的轉換，且日期為實際發佈日
- [ ] 版本號一致性已依 `VERSION_RULES.md` §7 逐項核對
- [ ] `README.md` 描述的功能與本次發佈內容一致
- [ ] 產物檔名完全符合 §2.1 的格式與字元限制

### 4.2 簽章與安全警告

- 可執行產物**建議**簽章（Windows 的 `signtool`、跨平台的 `osslsigncode` 等皆可）。
- 使用**自簽憑證**或未簽章時，`README.md` 的「常見問題」節**必須**說明：使用者可能看到作業系統或防毒的安全警告（例如 Windows SmartScreen）、為什麼會出現、如何確認檔案來源正確（對照校驗碼）。
- 憑證怎麼保管，看它**有沒有被任何地方信任**：

| 憑證 | 外流的後果 | 保管 |
| :--- | :--- | :--- |
| 自簽、沒有被加進任何信任清單或白名單，只是附上簽名 | 別人能簽出同樣不被信任的簽名，冒充不了什麼 | 憑證檔與密碼**可**進版控、**可**寫在建置腳本裡；**必須**在 `DEVELOPER.md` §9 註明「自簽、未被信任，不是機密」 |
| CA 簽發，或已被加進某處的信任清單（企業白名單、使用者的受信任根憑證） | 別人能簽出被信任的惡意檔 | **禁止**進版控（見 `DEVELOPER.md` §9）；密碼**禁止**寫死在建置腳本，**必須**從環境變數或本機不進版控的檔案讀取 |

- 自簽憑證一旦被加進任何信任清單，就改依第二列保管，並換一張沒外流過的憑證。
- 自簽的簽名不能證明檔案來源；文件**禁止**把它當成驗證手段，驗證一律靠校驗碼。
- 未簽章時**禁止**在文件中宣稱產物「已簽章」或「安全無虞」。

### 4.3 校驗碼

- 每次發佈**必須**提供所有產物的 **SHA-256** 校驗碼。
- **必須**以單一檔案 `<專案代號小寫>_v<版本號>_sha256sums.txt` 附在 Release 附件中，一行一個檔案：

```text
<64 位小寫十六進位雜湊>  myapp_v1.0.0_portable.exe
<64 位小寫十六進位雜湊>  myapp_v1.0.0_setup.exe
```

- 校驗碼**必須**由**實際上傳的那份檔案**計算，且在上傳後複驗一次。

### 4.4 Release 頁面

- 標題**必須**為 `<專案代號> v<版本號> Release`；1.0.0 之前的版本與帶預發佈標籤的版本寫 `<專案代號> v<版本號> Pre-release`，並**必須**勾選 Pre-release。
- 內文第一行**必須**是專案的顯示名「《<專案名稱>》(<專案代號>)」，接著是 `CHANGELOG.md` 中**該版本區塊的內容**，不含其他版本。
- 附件**必須**包含全部產物與校驗碼清單。
- 內文**禁止**貼上未整理的 git log。

範例（虛構專案 `MYAPP`）：

```text
標題：MYAPP v1.1.0 Release

《存檔編輯器》(MYAPP)

### Added (新增)
- 新增匯出報表功能，可在主畫面右上角找到。
```

### 4.5 舊版本的處置

**已發佈的 tag 與 Release**

- 正常情況下**必須**保留，讓使用者能取得舊版。
- 僅在舊發佈**不符合本規範命名慣例**、或內容有誤而必須撤下時，才刪除並重發；此時**必須**在新版本的 `CHANGELOG.md` 條目說明。

**被整個替換掉的舊實作**

- 依 `DEVELOPER.md` §8 的分支保留規則辦理：舊實作**必須**以分支保留，**禁止**直接刪除；主分支走新實作。
- 舊實作若是驗證新實作正確性的基準，**必須**在該基準比對通過後才解除保留。

## 5. 範例與註解慣例

- 佔位符**必須**用角括號加繁中描述：`<專案代號小寫>`、`<版本號>`、`<形式>`。
- 虛構專案一律用 `MYAPP`，虛構版本號一律 `v1.0.0`。
- 範例指令**必須**能原樣執行（佔位符除外），並同時提供 bash 與 PowerShell 兩種寫法。

建立與推送 tag：

```bash
git tag -a v1.0.0 -m "MYAPP v1.0.0 Release"
git push origin v1.0.0
```

產生校驗碼：

```bash
cd release
shasum -a 256 myapp_v1.0.0_* | grep -v sha256sums > myapp_v1.0.0_sha256sums.txt
```

```powershell
Get-ChildItem .\release\myapp_v1.0.0_* -Exclude *sha256sums* |
  Get-FileHash -Algorithm SHA256 |
  ForEach-Object { "$($_.Hash.ToLower())  $(Split-Path $_.Path -Leaf)" } |
  Out-File .\release\myapp_v1.0.0_sha256sums.txt -Encoding utf8
```

部署型建置 image：

```bash
docker build -t myapp:1.0.0 -t myapp:latest .
```

## 6. 禁止事項

- **禁止**在產物檔名使用大寫字母，或 `a-z0-9._-` 以外的字元（含中括號與空格）。
- **禁止**使用 §2.2 以外的形式標記。
- **禁止**在 tag 或產物檔名省略 `v` 前綴；**禁止**在 Docker image tag 加 `v`。
- **禁止**在同一版本重複發佈不同內容的產物。
- **禁止**未附校驗碼就發佈。
- **禁止**在 `CHANGELOG.md` 尚未更新的情況下建立 Release 或部署新版本號。
- **禁止**部署型專案部署新版本卻不打 tag。
- **禁止**把受信任的憑證（§4.2）、金鑰、密碼放進產物或版本控制，或寫死在建置腳本裡。
- **禁止**在 Release 內文貼上其他版本的變更內容。
- **禁止**直接刪除被替換掉的舊實作而不留分支。

## 7. 檢查清單

發佈型：

- [ ] §4.1 發佈門檻六項全部成立
- [ ] 產物形式與 `DEVELOPER.md` §7 所列完全相符，一種都沒少；能出 portable 的有 portable
- [ ] 每個產物檔名符合 `<專案代號小寫>_v<版本號>_<形式>`，全小寫、只用 `a-z0-9._-`
- [ ] tag 為 `v<版本號>`，建立在實際打包的 commit 上
- [ ] 需要簽章的產物已簽章；自簽或未簽時 README 已說明安全警告
- [ ] 受信任的憑證與密碼不在版控與腳本裡；進了版控的是未被信任的自簽憑證，且已在 `DEVELOPER.md` §9 註明
- [ ] 校驗碼清單涵蓋所有產物，且已於上傳後複驗
- [ ] Release 標題為 `<專案代號> v<版本號> Release`（1.0.0 前為 `Pre-release` 並已勾選）
- [ ] Release 內文第一行是顯示名，其後只含本版本的 `CHANGELOG.md` 區塊
- [ ] 舊 tag／Release 的處置已決定；若刪除，已在 `CHANGELOG.md` 說明
- [ ] 被替換的舊實作已依 `DEVELOPER.md` §8 建立保留分支
- [ ] 實機下載一次產物並驗證校驗碼與可執行性

部署型：

- [ ] `[Unreleased]` 已轉成版本區塊，版本號依 `VERSION_RULES.md` 遞增
- [ ] image 標了 `<專案代號小寫>:<版本號>`
- [ ] tag `v<版本號>` 建在部署的 commit 上並已推送
- [ ] 線上服務顯示的版本號與 tag 相同
