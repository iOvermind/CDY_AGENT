# DESIGN.md 撰寫規範

> 本規範規定 `DESIGN.md` **該寫什麼、怎麼寫**，以及哪些視覺決定必須跨專案一致。
> 格式以 impeccable 技能採用的 DESIGN.md 格式為準：YAML frontmatter 放 token，內文八個固定章節。
> 通用規範，任何有使用者介面的專案皆適用。取代舊的 `INTERFACE_RULES.md`。

---

## 1. 目的與適用範圍

### 1.1 目的

讓使用者介面的每一個數值都有**依據**可查，而不是每次憑感覺決定。

沒有這份文件時，典型的症狀是：上緣留白 24px、下緣 16px、左右 20px，因為當初只調了上緣就沒再回頭；兩顆並排的按鈕一顆 14px 一顆 12px，因為分別在不同時間加上去的。這類問題**不是**靠審美補救，而是靠「這裡該用多少」有唯一答案。

### 1.2 讀者

- 要**修改或新增畫面**的人。可以假設對方會寫 CSS，但不可假設對方知道這個專案的任何約定。
- 各專案裡的 **AI agent**。impeccable 的每個視覺指令開工前都會讀這份文件；frontmatter 的 token 也是它的 live 面板與檢查工具的資料來源。

### 1.3 本規範管什麼、不管什麼

- **管**：`DESIGN.md` 必須記錄哪些項目、用什麼格式、哪些項目必須跨專案一致。
- **不管**：**實作機制**。用 utility class、具名 CSS 類別、CSS-in-JS 還是別的，由專案自行決定——本規範只規定**值與關係**。
- **不管**：畫面該長什麼樣。版型與視覺世界是各專案自己的事（見 §4.2）。

### 1.4 邊界：`DESIGN.md` 只放視覺

| 問題 | 文件 |
| :--- | :--- |
| 怎麼用它 | `README.md` |
| 為誰做、為什麼做 | `PRODUCT.md` |
| **長什麼樣、怎麼互動** | **`DESIGN.md`（本規範）** |
| 怎麼改它、模組怎麼切 | `DEVELOPER.md` |

「design」一詞常被借去指別的東西，那些**不得**寫進 `DESIGN.md`，也**不得**佔用這個檔名：

| 內容 | 該去哪 |
| :--- | :--- |
| 模組公開 API、協議、存檔格式 | `DEVELOPER.md` §5；過長時外拆 `docs/API.md` |
| 遊戲機制、規則清單、平衡數值等領域規格 | `docs/` 下以內容命名（例如 `docs/MECHANICS.md`），由 `DEVELOPER.md` §5 連結 |
| 子系統的技術設計 | `docs/<主題>-design.md`，或寫成 ADR |

### 1.5 由哪個技能維護

| 情況 | 指令 |
| :--- | :--- |
| 已有畫面，要把現況記下來 | `/impeccable document`（scan mode：從程式碼抽 token，再問描述性的用詞） |
| 還沒寫程式，先定視覺方向 | `/impeccable document --seed`（產出標了 `SEED` 的種子版，之後再跑一次 scan） |
| 把散落的值收成 token 與元件 | `/impeccable extract` |
| 檢查畫面與 `DESIGN.md` 是否一致 | `/impeccable audit`、`/impeccable polish` |

impeccable 另外產生 `.impeccable/design.json`（sidecar），放 frontmatter 裝不下的東西（色階、陰影、動態、元件 HTML/CSS 片段）。它**由技能產生，禁止手改**；`DESIGN.md` 改了就重跑 `/impeccable document` 更新它。

`DESIGN.md` 的前提是 `PRODUCT.md`（見 `PRODUCT_RULES.md`）：先有產品事實，再定視覺。

### 1.6 強制語彙

| 用詞 | 意義 |
| :--- | :--- |
| **必須** | 不做就是不合規（MUST） |
| **建議** | 有更好的理由才可以不做（SHOULD） |
| **可** | 自行斟酌（MAY） |

## 2. 檔案位置與命名

- 檔名**必須**為 `DESIGN.md`，**必須**放在 `docs/`（impeccable 會到這裡找）。
- 條文中提到其他文件時只寫檔名；實際位置見 `DEVELOPER_RULES.md` §1.3 的文件地圖。
- 編碼**必須**為 **UTF-8 無 BOM**，換行**必須**為 **LF**，檔尾**必須**留一個換行。
- `PRODUCT.md` 的 `## Platform` 為 `none`（沒有使用者介面）的專案**不需要**這份文件；但若有終端機彩色輸出，仍**必須**遵守 §4.8 的日誌等級。

### 2.1 語言

技能靠固定的英文標記解析這份文件，翻譯就讀不到。下列項目**必須**逐字使用英文原文，其餘內文**必須**為**繁體中文**：

| 項目 | 原文 |
| :--- | :--- |
| frontmatter 的鍵 | `name`、`description`、`colors`、`typography`、`rounded`、`spacing`、`components` 及其子鍵 |
| frontmatter 的 `name` | 專案的顯示名 `《<專案名稱>》(<專案代號>)` |
| H1 | `# Design System: 《<專案名稱>》(<專案代號>)` |
| 八個 H2 | 見 §3.2 |
| 北極星 | `**Creative North Star: "<名稱>"**`（引號內可用中文） |
| 特徵清單 | `**Key Characteristics:**` |
| 具名守則 | `**The <英文名> Rule.**`，後接繁中內文 |
| 守則小節 | `### Named Rules` |
| 該做／不該做 | `### Do:`、`### Don't:`，條目以 `**Do**`／`**Don't**` 開頭 |

token 名稱、CSS 屬性、單位保留原文。

### 2.2 從 `INTERFACE.md` 遷移

1. 確認舊 `INTERFACE.md` 寫的是視覺規格。若寫的是模組 API 或協議，**不**遷移成 `DESIGN.md`，改依 §1.4 搬到 `DEVELOPER.md` §5 或 `docs/API.md`。
2. 依 §3.3 的對照表把八章搬進新結構，數值逐字保留。
3. 把 token 補進 frontmatter（§3.1）。
4. 新檔放在 `docs/DESIGN.md`；刪除 `INTERFACE.md`，**禁止**兩份並存；全庫搜尋 `INTERFACE.md` 改連結。
5. 若已安裝 impeccable，跑 `/impeccable document` 產生 sidecar，並讓它比對程式碼與文件的差異。

### 2.3 共用 token 與系列

**系列**（series）指一連串有關聯、要看起來像同一套東西的專案，它們共用同一份 token 檔。本規範規定的是**共用的機制**，不是特定的色值。

每個專案**必須**在 `## Overview` 表明自己屬於哪一種情況：

**獨立專案**——不屬於任何 系列：

- token 值由該專案自行決定，**必須**在 `DESIGN.md` 完整記錄。
- **可**直接採用 [`tokens.css`](tokens.css) 當起點，也**可**完全自訂。

**屬於某個 系列 的專案**：

- **必須**與該 系列 的其他專案共用同一份 token 檔，且**逐字相同**。
- **必須**在 `## Overview` 指明所屬 系列 與該 token 檔的來源。
- **必須**直接引用或原樣複製該檔，**禁止**手抄色值到樣式程式碼。
- **禁止**單一專案自行偏離其中幾個值——逐項偏離會讓「逐字相同」失去驗證意義。要改就改整個 系列。
- 修改**必須**同步套用到 系列 內的全部專案，並以雜湊比對驗證：
  ```powershell
  Get-FileHash <各專案>\docs\rules\tokens.css -Algorithm SHA256
  ```

**token 檔與 frontmatter 的對應**：token 檔是執行期的來源，frontmatter 是給人與技能讀的同一組值。frontmatter `colors` 的鍵**必須**是 token 檔的變數名去掉 `--token-color-` 前綴（`--token-color-surface-container-low` → `surface-container-low`），值**必須**與 token 檔逐字相同。

[`tokens.css`](tokens.css) 是一份**可直接使用的預設起點**（深色配色），不是強制的正典。

## 3. 結構

判準是：**照這份文件就能把畫面重建出來**。

### 3.1 Frontmatter：token 的正本

檔案**必須**以 YAML frontmatter 開頭，只允許下列七個頂層鍵：

| 鍵 | 內容 | 必要 |
| :--- | :--- | :-: |
| `name` | 專案名稱 | 必須 |
| `description` | 一句話描述 | 必須 |
| `colors` | 每個色一條，鍵為描述性名稱 | 有就必須 |
| `typography` | 每種字級用途一條（物件：`fontFamily`、`fontSize`、`fontWeight`、`lineHeight`、`letterSpacing`） | 有就必須 |
| `rounded` | 圓角檔位 | 有就必須 |
| `spacing` | 語意間距，鍵為用途名稱（見 §4.4） | 有就必須 |
| `components` | 每個元件變體一條（`button-primary`、`button-primary-hover`） | 建議 |

規則：

- 引用其他 token 用 `{colors.primary}` 這種寫法。`components` **可**引用基本 token；基本 token 之間**禁止**互相引用。
- `components` 每條只能用八個屬性：`backgroundColor`、`textColor`、`typography`、`rounded`、`padding`、`size`、`height`、`width`。陰影、焦點框、動態、模糊放不進來，寫在內文表格（§4.1）。
- **禁止**自創頂層鍵（`motion:`、`shadows:`、`opacity:` 都不行）——解析器只認上面七個。
- 只列實際用到的值。用不到的鍵整個省略，**禁止**放空殼或預留值。
- 種子版（seed）只有 `name` 與 `description`，第一行**必須**是 impeccable 的 `<!-- SEED: … -->` 註記。

### 3.2 八個必要章節（依此順序）

H1 之後**必須**依序出現下列八個 H2，**章名逐字如左欄**：

| # | 章節 | 必須回答的問題 |
| :-: | :--- | :--- |
| 1 | `## Overview` | 創意北極星？畫面型態、預設與最小尺寸、可否縮放？獨立專案或屬於哪個 系列？整體性格與關鍵特徵？ |
| 2 | `## Colors` | 有哪些色、各自的描述名與用途？哪些是共用 token？日誌等級用哪些色？ |
| 3 | `## Typography` | 字體堆疊？每種用途（H1、H2、內文、標籤、等寬…）的字級、字重、行距？ |
| 4 | `## Layout` | 每種語意間距的名稱、值、用於何處？版型示意與各區塊職責？斷點？ |
| 5 | `## Elevation & Depth` | 層次靠什麼表現？不透明度有哪幾檔？光暈／模糊／漸層／陰影用了沒、用在哪、強度多少？ |
| 6 | `## Shapes` | 圓角有哪幾檔、各用在哪？邊框與外框的語言？ |
| 7 | `## Components` | 控制項尺寸？按鈕角色與各狀態？焦點、hover、停用、載入、錯誤怎麼表現？日誌／訊息怎麼呈現？各主要元件？ |
| 8 | `## Do's and Don'ts` | 本專案確立的視覺守則，該做與不該做？ |

**沒有用到的章節必須保留標題，內文寫「未使用」並說明現況，不得刪除。** 這樣才分得出「刻意不用」與「忘了寫」——這是本規範最重要的一條。章內的子表同理：例如沒用光暈，光暈那一列寫「未使用」，不得刪列。

### 3.3 與舊 `INTERFACE.md` 的章節對照

| 舊 `INTERFACE.md` | 新 `DESIGN.md` |
| :--- | :--- |
| 1 適用範圍與視窗尺寸 | `## Overview` 的「畫面型態」表 |
| 2 色票 | frontmatter `colors` ＋ `## Colors` |
| 3 字體與字級 | frontmatter `typography` ＋ `## Typography` 的字級表 |
| 4 間距 | frontmatter `spacing` ＋ `## Layout` 的語意間距表 |
| 5 控制項（尺寸、按鈕角色與狀態） | frontmatter `rounded`、`components` ＋ `## Shapes` ＋ `## Components` |
| 6 視覺效果（不透明度、光暈／模糊／漸層） | `## Elevation & Depth` |
| 7 狀態與回饋、日誌等級 | `## Components` 的「狀態與回饋」與「日誌與訊息」 |
| 8 畫面結構 | `## Layout` 的版型示意與區塊職責 |
| （無） | `## Do's and Don'ts`：原本散在各章的「不得」收到這裡 |

### 3.4 選用內容

放在對應章節底下的 H3，不另開 H2：

| 內容 | 放在 |
| :--- | :--- |
| 動畫與轉場的時間與曲線 | `## Components` 的 `### Motion` |
| 圖示來源與尺寸 | `## Components` 的 `### Icons` |
| 響應式斷點 | `## Layout` |
| 本專案的招牌元件 | `## Components`，一個元件一個 H3 |
| 文案與用詞慣例 | `## Do's and Don'ts`；名詞本身寫在 `GLOSSARY.md` |

## 4. 撰寫規則

### 4.1 Frontmatter 與內文表格的關係

- frontmatter 是 token 的**正本**。內文表格**可**列出同一個值方便閱讀，但**必須**與 frontmatter 逐字相同；不一致時以 frontmatter 為準，並修正表格。
- frontmatter 放不下的值——不透明度檔位、焦點框、陰影、模糊、動態——以內文表格為正本，且只寫在一處。
- 每個值**必須**先給描述，再把精確值放括號：「控制項圓角（6px）」，而不是只寫 `rounded-md`。

### 4.2 跨專案的一致性分級

每一項視覺決定**必須**歸入下列三級之一。同一 系列 的專案要看起來像同一套東西，靠的是第一級。

獨立專案（§2.3）沒有共用對象，第一級對它的意義是「**這些項目必須有唯一解並記錄下來**」——不得散落在各處各寫各的。

**必須共用**——逐字相同，不得自訂：

| 項目 | 為什麼 |
| :--- | :--- |
| 色票 token 的名稱與色值 | 這是「同一系列」最直接的來源 |
| 字體堆疊（sans / mono） | 字體一換，親緣感立刻消失 |
| 不透明度檔位 | 決定層次的表現方式 |
| 焦點樣式與停用表現 | 同一套互動語彙，換一個程式不用重學 |
| 日誌／訊息等級的名稱與配色 | 跨程式、跨語言的契約 |

**建議共用**——偏離時**必須**在 `DESIGN.md` 寫明理由：

- 字級表與行距
- 語意間距的名稱與值
- 控制項高度與圓角

**各自決定**——**禁止**互相套用：

- 創意北極星與視覺世界
- 版型與畫面結構
- 視窗尺寸
- 有哪些區塊、怎麼排

> 體量差距大的專案硬套同一套版型只會難用。工作站型的編輯器與按一下就跑完的小工具，共用色票已足以看出是同一系列。

### 4.3 字級必須綁定用途

`## Typography` **必須**有一張字級表，為每一種用途綁定**唯一**的 token：

```markdown
| 用途 | Token | 字級 | 字重 | 行距 | 字體 |
| :--- | :--- | ---: | ---: | ---: | :--- |
| H1 應用程式標題 | `headline` | 16px | 700 | 1.2 | sans |
| H2 區塊標題 | `title` | 14px | 500 | 1.4 | sans |
| 內文／按鈕 | `body` | 14px | 400 | 1.5 | sans |
| 欄位標籤 | `label` | 12px | 400 | 1.4 | sans |
```

規則：

- 頁面上有的標題層級（H1、H2、H3…）**必須**各有一列；沒有的層級不列。
- **禁止**使用表外的字級。真的需要新的值，**必須**先修改這張表與 frontmatter。
- 等寬字體只用於路徑、雜湊、日誌、程式碼、數字欄位。

### 4.4 間距必須語意化

**禁止**只給一串可用數值就了事——那樣「上緣用 24、下緣用 16」依然合規，問題不會消失。

frontmatter `spacing` 的鍵**必須**是用途名稱（`window-edge`、`block-gap`），**禁止**用 `sm`、`md` 這類尺寸名。`## Layout` **必須**為每一種用途綁定**唯一**的值：

```markdown
| 名稱 | Token | 值 | 用於 |
| :--- | :--- | ---: | :--- |
| 視窗外緣 | `window-edge` | 20px | 內容距視窗四邊（上下左右一律相同） |
| 區塊間 | `block-gap` | 12px | 主要區塊之間 |
| 控制項間 | `control-gap` | 8px | 同一列的控制項之間 |
```

規則：

- **四邊外緣必須相等**，**禁止**單獨加大某一邊。
- **禁止**使用表外的值。真的需要新的值，**必須**先修改這張表與 frontmatter。

### 4.5 同一列的控制項必須對齊

同一列的輸入框、下拉、按鈕**必須**高度相同、字級相同。**寬度可以不同。**

### 4.6 按鈕

- **必須**定義角色（至少「主要」與「次要」）與各角色的外觀，並在 frontmatter `components` 各有一條。
- **必須**定義四種狀態：hover、active、disabled、進行中。
- 每個畫面**最多一個**主要按鈕。
- 按鈕文字**建議**用動詞，避免「確定」這類看不出後果的字。

### 4.7 焦點必須可見

- 所有可以用 Tab 走到的元件**必須**有可見的焦點樣式。
- **禁止**只寫 `outline: none` 而不補替代樣式——那會讓鍵盤使用者完全看不出焦點在哪。
- 焦點樣式屬於「必須共用」（§4.2）。

### 4.8 日誌／訊息等級：名稱與顏色都要，且**禁止**只靠顏色

§4.2 把「日誌／訊息等級的名稱與配色」列為必須共用。**配色**在 token 檔裡（`--token-color-level-*`），**名稱**則由下表規定——兩半都是契約的一部分。本節同樣適用於沒有 `DESIGN.md` 的命令列專案。

| 等級 | 識別字串 | 中譯 | 語意 |
| :--- | :--- | :--- | :--- |
| debug | `DEBUG` | 除錯 | 只在排查問題時需要的細節，預設不顯示 |
| info | `INFO` | 資訊 | 一般進度與結果回報 |
| warn | `WARN` | 警告 | 可以繼續，但使用者應該知道 |
| error | `ERROR` | 錯誤 | 動作失敗或中止 |

規則：

- 這四檔是一條**嚴重度軸線**，對齊 syslog / Python `logging` / Rust `log`。**禁止**把「成功」塞進來——它不是嚴重度，用 `--token-color-status-success`。
- 識別字串**必須**全大寫、逐字如上。**禁止**自創（`WARNING`、`ERR`、`FATAL`、`SUCCESS` 都不行），否則跨程式的日誌無法一起 grep。
- **禁止**只靠顏色傳達等級。理由有二：stdout 導向檔案或在不支援 ANSI 的終端時顏色會消失，等級資訊跟著消失；且只靠顏色傳達資訊不符合無障礙要求。
- 因此每一則訊息**必須**同時帶識別字串或等價的文字前綴（`[!]`、`[x]` 之類），顏色只是**增強**，不是資訊的唯一管道。
- 需要新增等級時**必須**先更新本表與 token 檔，不得在單一專案臨時發明。

### 4.9 視覺效果要記錄，不是要禁止

光暈、高斯模糊、漸層、陰影**不禁止**，但**用了就必須**在 `## Elevation & Depth` 寫明：用在哪、強度數值多少。沒用**必須**寫「未使用」。

理由是可預期性：效果本身沒有錯，但「這裡的模糊是 8px 還是 12px」如果沒有答案，下一個人只能再憑感覺加一個。

### 4.10 具名守則與北極星

- `## Overview` **必須**以創意北極星開頭：一個具名的比喻，概括整個視覺系統（「工作台上的量具」「蓋滿章的護照」）。它由使用者選定，**禁止**由 agent 自行決定後直接寫入。
- 具名守則（`**The <英文名> Rule.**`）用來記錄**已確立**的不變量：每章一到三條，一條一句話講完規則，必要時再補理由。
- 守則與 Do's and Don'ts **必須**有依據：程式碼裡的現況，或使用者確認過的決定。**禁止**把單一頁面的臨時決定升格成全系統守則。

### 4.11 一般撰寫規則

- 應用程式的視窗標題與關於畫面**必須**顯示專案的顯示名「《專案名稱》(專案代號)」，**可**接版本號。
- 規格**必須**用表格，不用散文；性格與理由才用段落。
- 全文**只有一個** H1；必要章節用 H2，章內細項用 H3。
- 數值**必須**帶單位。
- 色值**必須**寫完整的十六進位或 token 名稱，**禁止**只寫「深灰」。
- 色彩依角色分組（Primary／Secondary／Tertiary／Neutral），不依色相排。只有一個強調色就只寫 Primary 與 Neutral，不硬湊。
