# PRODUCT.md 撰寫規範

> 本規範規定 `PRODUCT.md` **該寫什麼、怎麼寫**。
> 格式以 impeccable 技能的 product record（`<!-- impeccable:product-schema 1 -->`）為準。
> 通用規範，任何專案皆適用。

---

## 1. 目的與適用範圍

### 1.1 目的

把**產品的事實**——為誰做、解決什麼、憑什麼不同、不能違反什麼——寫在一個地方，讓之後的每個決定（功能、文案、視覺、取捨）都有依據可查。

沒有這份文件時，典型的症狀是：每次請 agent 做畫面或寫文案，都要重講一遍「使用者是誰」；或者 agent 自己猜，猜出一個不存在的客群、一句沒人承諾過的賣點。

### 1.2 讀者

- 要**做決定**的人：加不加這個功能、這句文案能不能寫、這個畫面為誰設計。
- 各專案裡的 **AI agent**。impeccable 的每個指令開工前都會讀這份文件；它就是 agent 對這個產品的全部認識。

### 1.3 邊界

| 問題 | 文件 |
| :--- | :--- |
| 怎麼用它 | `README.md` |
| **為誰做、為什麼做** | **`PRODUCT.md`（本規範）** |
| 長什麼樣 | `DESIGN.md` |
| 怎麼改它 | `DEVELOPER.md` |
| 名詞是什麼意思 | `GLOSSARY.md` |
| 為什麼這樣決定 | `docs/adr/` |

`PRODUCT.md` **不含視覺**：色彩、字體、版型、元件、頁面構想一律寫在 `DESIGN.md`。

### 1.4 由哪個技能維護

**impeccable 的 `init`**（`/impeccable init`）負責建立與更新本文件：先讀專案，再用可點選的選項問使用者，最後寫入。人工撰寫時**必須**照本規範的章名，否則技能讀不到。

### 1.5 強制語彙

| 用詞 | 意義 |
| :--- | :--- |
| **必須** | 不做就是不合規（MUST） |
| **建議** | 有更好的理由才可以不做（SHOULD） |
| **可** | 自行斟酌（MAY） |

## 2. 檔案位置與命名

- 檔名**必須**為 `PRODUCT.md`，**必須**放在 `docs/`（impeccable 會到這裡找）。
- 條文中提到其他文件時只寫檔名；實際位置見 `DEVELOPER_RULES.md` §1.3 的文件地圖。
- 編碼**必須**為 **UTF-8 無 BOM**，換行**必須**為 **LF**，檔尾**必須**留一個換行。
- **每個專案都必須有**這份文件，不論有沒有使用者介面。
- 單一儲存庫內有多個獨立產品（monorepo）時，**可**在子產品目錄放各自的 `PRODUCT.md`；`docs/PRODUCT.md` 只寫共用的部分。

### 2.1 語言

- H1 與 H2 **必須**用 §3 規定的英文原文——那是技能解析的錨點，翻譯或改字就讀不到。
- 內文**必須**為**繁體中文**；指令、檔名、專有名詞保留原文。

---

## 3. 結構：必要章節 / 選用章節

H1 **必須**為 `# Product`，下一行**必須**是版本註記，逐字如下（這是技能要求的固定標題，不換成專案的顯示名；顯示名「《專案名稱》(專案代號)」寫在 `## Product Purpose` 的第一句）：

```markdown
# Product

<!-- impeccable:product-schema 1 -->
```

### 3.1 必要章節（依此順序）

| # | 章節 | 必須回答的問題 |
| :-: | :--- | :--- |
| 1 | `## Platform` | 產品的使用者介面跑在哪？（見 §4.2） |
| 2 | `## Users` | 主要使用者是誰？在什麼情境下、要完成什麼事？ |
| 3 | `## Product Purpose` | 它做什麼、為什麼存在？**成功的定義**是什麼？ |
| 4 | `## Positioning` | 有什麼是鄰近的產品**無法如實照抄**的？ |
| 5 | `## Capabilities and Constraints` | 確定的功能、技術限制、不得違反的約束、尚未決定的事？ |

必要章節沒有答案時**必須**保留標題，寫「未定」並說明原因（例如「刻意保留，待 docs/SCORING.md 流程決定」）。

### 3.2 選用章節

出現時**必須**依此相對順序穿插在必要章節之間（完整順序見範本）：

| 章節 | 放在 | 什麼時候寫 |
| :--- | :--- | :--- |
| `## Stack` | Platform 之後 | 新專案尚無程式碼時，記錄使用者對技術棧的決定；已有程式碼就**不寫**（看 `DEVELOPER.md`） |
| `## Operating Context` | Positioning 之後 | 使用時實際牽涉的流程、環境、工具、文件或儀式 |
| `## Brand Commitments` | Capabilities 之後 | 已存在的名稱、語氣、標誌、身分約束，或使用者明確綁定的參考 |
| `## Evidence on Hand` | Brand Commitments 之後 | 手上有的真實內容、資料、示範、素材（附路徑），以及**沒有**、不得捏造的東西 |
| `## Product Principles` | Evidence 之後 | 三到五條由使用者確認過的策略原則 |
| `## Accessibility & Inclusion` | 最後 | 已知的使用者需求或要求的標準 |

選用章節與專案無關時**直接省略**，不寫空殼。

## 4. 撰寫規則

### 4.1 只寫確認過的事實

- 每一條**必須**有來源：使用者親口確認，或儲存庫裡查得到的證據（README、ADR、程式碼）。
- 從證據推得、尚未經使用者確認的，**必須**在句尾標「（推測，待確認）」。
- 還沒決定的事**必須**寫成「未定：<什麼事>」，**禁止**替使用者發明答案。
- **禁止**捏造客戶、推薦語、效能數字、價格、授權或部署聲明。手上沒有就在 `## Evidence on Hand` 寫「沒有」。

### 4.2 Platform 的值

第一行**必須**是下列其中一個值，單獨成行、不加修飾：

| 值 | 意義 |
| :--- | :--- |
| `web` | 使用者介面以 web 技術呈現：瀏覽器、PWA，以及 Tauri、Wails、Electron 這類包網頁的桌面殼 |
| `ios` | 原生 iOS 設計語言 |
| `android` | 原生 Android 設計語言 |
| `adaptive` | 同一個產品依作業系統切換原生設計語言 |
| `none` | 沒有使用者介面（CLI、函式庫、服務、文件庫） |

- 手機網頁仍是 `web`；包一層原生殼的網站也仍是 `web`。
- `none` 表示不跑 impeccable 的視覺流程，專案也**不需要** `DESIGN.md`。impeccable 不認得這個值，讀到時會印一行 WARNING 並當成 `web` 處理；這是刻意的取捨——值要如實，警告不影響功能，**不得**為了消除警告改寫成 `web`。
- 值的下一段**可**用括號補充說明（例如「網站是 web；印刷品不屬於任何值」）。

### 4.3 Users：寫情境與工作，不寫人口統計

- **必須**寫出「誰、在什麼情境、要完成什麼事」三者。
- 有多種使用者時，**必須**區分主次，用粗體名稱開頭的條列。
- **禁止**只寫「一般使用者」「所有人」。

### 4.4 Product Purpose：成功要可判斷

**必須**以一句「成功＝……」收尾，寫成事後能判斷達成與否的狀態。

### 4.5 Positioning：寫機制，不寫形容詞

**必須**寫「憑什麼不同」的機制或事實，**禁止**只寫「簡單」「強大」「好用」。內部工具沒有競品時，寫它取代了什麼（手動流程、試算表、舊系統）。

### 4.6 不寫進這份文件的東西

| 內容 | 該去哪 |
| :--- | :--- |
| 色彩、字體、版型、元件、視覺參考 | `DESIGN.md` |
| 單一頁面的敘事、CTA、訪客模式 | impeccable 的 surface brief（`.impeccable/surfaces/`） |
| 建置步驟、目錄、架構 | `DEVELOPER.md` |
| 名詞定義 | `GLOSSARY.md` |
| 決策的理由與替代方案 | `docs/adr/` |
| 使用步驟 | `README.md` |

`PRODUCT.md` **可**一句話提及上述文件並連結，**禁止**複述其內容。

### 4.7 一般撰寫規則

- 全文**只有一個** H1。
- 章節用條列與短段落，不用表格以外的版面裝飾。
- 庫內連結**必須**用相對路徑。
- 版本註記的數字只在 impeccable 改版其範本時更新。

## 5. 範例與註解慣例

- 佔位符**必須**用角括號加繁中描述：`<主要使用者>`、`<成功的定義>`。
- 虛構專案一律用 `MYAPP`。
- 範本內的 HTML 註解是填寫說明，填完**必須**刪除；版本註記 `<!-- impeccable:product-schema 1 -->` **不得**刪除。

---

## 6. 禁止事項

- **禁止**翻譯或改寫 §3 規定的 H1、H2 與版本註記。
- **禁止**寫入視覺決定（色彩、字體、版型、元件）。
- **禁止**捏造客戶、推薦語、數據、價格、授權、部署聲明。
- **禁止**把推測寫成事實——要標「（推測，待確認）」。
- **禁止**刪除沒有答案的必要章節——要寫「未定」。
- **禁止**在 `## Platform` 寫 §4.2 以外的值。
- **禁止**只用形容詞描述定位。

- [ ] 五個必要章節齊全、順序正確，沒有答案的寫「未定」
- [ ] 選用章節的相對順序正確，無關的已省略
