# README 與專案門面撰寫規範

> 本規範規定使用者第一眼看到的東西——`README.md` 與儲存庫的 **About**——
> **該寫什麼、怎麼寫**，不規定專案的技術選型。
> 通用規範，任何專案皆適用。

---

## 1. 目的與適用範圍

### 1.1 目的

讓任何人在**三十秒內**判斷「這個東西是不是我要的」，並在**五分鐘內**真的用起來。

### 1.2 讀者

README 的讀者是**使用者**——也就是**這個產物的消費者**：

| 專案型態 | 使用者是誰 |
| :--- | :--- |
| 桌面 / 行動應用程式 | 操作它的人 |
| 函式庫 (library) | 在自己專案裡引用它的開發者 |
| 命令列工具 (CLI) | 在終端機執行它的人 |
| 服務 / API | 呼叫它的人 |
| 自架服務（部署型） | 架設它的人，以及透過瀏覽器使用它的人 |
| 內部工具 | 組織內操作它的人 |

### 1.3 邊界

用**「用它」還是「改它」**切，不用「技術/非技術」切：

- **用它** → `README.md`
- **改它** → `DEVELOPER.md`

其他問題各有自己的文件（為誰做 → `PRODUCT.md`、使用者介面長什麼樣 → `DESIGN.md`、名詞 → `GLOSSARY.md`、各主機怎麼架 → `DEPLOY.md`），完整的文件地圖見 `DEVELOPER_RULES.md` §1.3。

因此環境建置、建置指令、測試、目錄結構、架構說明**一律不進 README**（見 §6）。

### 1.4 為什麼 About 也歸這份管

儲存庫的 **About**（簡介、網站、主題標籤）不是檔案，卻是**比 README 更早被看到**的東西——它出現在搜尋結果、Star 清單、分享連結的預覽裡。

它與 README 的「一句話定位」講的是同一件事，分開管的結果就是各寫各的：README 改了、About 留在半年前的版本，而**沒有人會發現**。所以兩者寫在同一份規範裡，並要求逐字一致（見 §4.7）。

### 1.5 本規範不管什麼

- 不管專案用什麼語言、框架、建置工具
- 不管 README 的視覺風格（emoji、徽章、排版偏好由專案自訂）
- 不管 `DEVELOPER.md`、`CHANGELOG.md`、`DEPLOY.md` 的內容（各見其規範或 §4.10）
- 不管儲存庫的其他設定（分支保護、labels、可見性）

### 1.6 強制語彙

| 用詞 | 意義 |
| :--- | :--- |
| **必須** | 不做就是不合規（MUST） |
| **建議** | 有更好的理由才可以不做（SHOULD） |
| **可** | 自行斟酌（MAY） |

## 2. 檔案位置與命名

- 檔名**必須**為 `README.md`，**必須**放在儲存庫**根目錄**。
- 編碼**必須**為 **UTF-8 無 BOM**，換行**必須**為 **LF**，檔尾**必須**留一個換行。
- 語言**必須**為**繁體中文**；指令、檔名、API 名稱、專有名詞保留原文，首次出現時加中譯。
- 條文中提到其他文件時只寫檔名；`README.md` 在根目錄，其餘文件在 `docs/`（見 `DEVELOPER_RULES.md` §1.3），README 裡的連結**必須**寫成 `docs/<檔名>`。

### 2.1 內容外拆

單一章節過長時，**可**把細節拆到 `docs/` 底下（例如 `docs/MANUAL.md`、`docs/DEPLOY.md`），但：

- §3 的每個必要章節**必須**在 README 保留**標題與至少一段摘要**，再連結過去。
- **禁止**把 README 縮成只有連結的目錄頁。

### 2.2 About 存在哪裡

About 不是檔案，是儲存庫的設定。它沒有版本控制，**改了不會留下紀錄，也不會有人 review**——這正是它容易過時的原因，所以 §7 的檢查清單把它列為發佈前必查項。

公開與私有儲存庫的 About **一律**照本規範填寫：私有的日後可能公開，到時才補就會漏。

## 3. 結構：必要章節 / 選用章節

### 3.1 必要章節（依此順序）

| # | 標題（逐字） | 必須回答的問題 |
| :-: | :--- | :--- |
| 1 | `# 《<專案名稱>》(<專案代號>)` ＋ 一句話定位 | 這是什麼？給誰用？ |
| 2 | `## 這是什麼` | 它解決什麼問題？有哪些主要功能？ |
| 3 | `## 取得與安裝` | 怎麼拿到它？需要什麼環境？怎麼裝或架起來？（見 §4.10） |
| 4 | `## 快速開始` | 從裝好到看見結果，最短路徑是什麼？ |
| 5 | `## 常見問題` | 卡住了怎麼辦？ |
| 6 | `## 授權` | 我能拿它做什麼？（見 §4.11） |
| 7 | `## 開發者` | 我想改它，去哪？（連結 `docs/DEVELOPER.md` 與 `docs/CHANGELOG.md`） |

標題**必須**逐字如上——測試與 agent 靠標題找章節，「開發者入口」「常見問題 / 疑難排解」這類變體都不合規。順序**不得**調換。沒有內容的必要章節**必須**保留標題並註明現況（例如「目前無已知問題」），**不得**刪除。

### 3.2 選用章節

| 章節 | 標題（逐字） | 放置位置 |
| :--- | :--- | :--- |
| 截圖 / 操作動畫 | 不另立標題 | 第 2 節之內 |
| 相容性對照表 | 不另立標題 | 第 3 節之內 |
| 操作指南 | `## 操作指南` | 第 4 節之後；超過 100 行**建議**外拆 `docs/MANUAL.md`，此處留摘要與連結 |
| 已知限制 | `## 已知限制` | 第 5 節之前 |
| 致謝與來源參考 | `## 致謝與來源參考` | 第 6 節之前 |

### 3.3 About 的欄位

| 欄位 | 必要性 | 內容 |
| :--- | :--- | :--- |
| 簡介（description） | **必填** | 與 README 的一句話定位**逐字相同**（見 §4.7） |
| 主題標籤（topics） | **必填** | 涵蓋三個面向，見 §4.8 |
| 網站（website） | 選填 | 只填「離開這個儲存庫也能用」的東西，見 §4.9 |

## 4. 撰寫規則

### 4.1 語氣與人稱

- 對使用者用「你」，不用「您」「使用者」「本人」。
- 用祈使句寫步驟：「按下開始」，不是「使用者可以按下開始按鈕」。
- 陳述事實，不推銷。**禁止**「業界領先」「完美支援」這類無法驗證的形容。

### 4.2 標題層級

- 全文**只有一個** H1（`#`），即專案的顯示名「《<專案名稱>》(<專案代號>)」。
- 必要章節用 H2（`##`），其下最多再兩層（H3、H4）。**禁止** H5 以下。

### 4.3 程式碼區塊

- **必須**標註語言（```bash、```powershell、```json…）。
- 指令**必須**一行一條，**禁止**帶提示符（`$`、`>`、`PS>`），使用者才能整段複製。
- 需要說明的指令用行內註解，不要在區塊外另寫一段。

### 4.4 連結與圖片

- 庫內連結**必須**用相對路徑（`docs/使用說明.md`），**禁止**寫成絕對網址或本機路徑。
- 圖片**必須**放在庫內（建議 `docs/images/`），**必須**有替代文字。
- 外部連結**必須**寫清楚指向何處，**禁止**只寫「連結」「這裡」。

### 4.5 表格

規格、相容性、對照關係用表格，不用巢狀項目符號。

### 4.6 長度

必要章節齊全的前提下越短越好。超過 200 行時**建議**依 §2.1 外拆。

### 4.7 一句話定位與 About 簡介

README 第一節的一句話定位，與 About 的簡介**必須逐字相同**。

因此定位句**必須是純文字**——**禁止**使用 `` `程式碼` ``、`**粗體**`、連結或任何 Markdown 語法，否則貼進 About 會變成一串符號。

**結構**：

```text
<這是什麼>。<對使用者的價值>。
```

- 先講「這是什麼」，讓人判斷是不是自己要的；再講「對使用者的價值」，讓人知道值不值得下載。
- 長度**建議** 60 字以內，**上限** 100 字。
- **禁止**寫技術棧（「採用 TypeScript 與 Vite 建構」）——這是給使用者看的，不是給從業人員。技術棧寫在 `DEVELOPER.md`。
- **禁止**無法驗證的形容（「現代化」「流暢」「業界領先」），與 §4.1 一致。
- 尚未可用的專案**必須**在句中講明，例如「本專案剛起步，還沒有可用的版本」。
- **必須**與 `PRODUCT.md` 的 Product Purpose、Positioning 一致——定位句是它寫給使用者的一句話版本。

範例（虛構專案 `MYAPP`）：

```text
MYAPP 的存檔編輯器。選好資料夾按一下，就能改角色數值並直接寫回遊戲。
```

### 4.8 主題標籤

topics 決定別人搜不搜得到這個專案。**必須**涵蓋三個面向，每個面向至少一個：

| 面向 | 回答的問題 | 例子 |
| :--- | :--- | :--- |
| 領域 / 對象 | 別人找這類東西會打什麼？ | `monopoly`、`dos-game` |
| 專案型態 | 這是什麼樣的東西？ | `map-editor`、`game-patch`、`cli` |
| 主要技術 | 用什麼做的？ | `tauri`、`rust`、`typescript` |

- **建議** 3–6 個（平台上限 20 個）。
- **必須**全部小寫，詞間用連字號。
- **同一系列的專案必須共用至少一個 topic**，否則從其中一個找不到其他的。

### 4.9 網站

- 只填**離開這個儲存庫也能用**的東西：線上版、文件站、專案首頁。
- **禁止**填儲存庫自己的網址或 Releases 頁面——平台上已經顯示了，重複一次只是讓使用者點了一圈回到原地。
- 沒有這種東西就**留空**。留空是合規的，填錯不是。

### 4.10 取得與安裝的四種情形

「取得與安裝」寫的是**使用者實際拿到它的方式**。依專案型態，**必須**照下表寫：

| 情形 | 這一章寫什麼 | 細節放哪 |
| :--- | :--- | :--- |
| 發佈型（下載產物） | 系統需求、下載位置（Releases）、各產物形式的用途、安裝步驟；有 portable 時先列 portable | — |
| 部署型（自架服務） | 系統需求與**最短的部署路徑**（例如 `docker compose up -d` 前要準備的設定） | 依主機而異的細節（反向代理、通道、備份、各站設定）外拆 `docs/DEPLOY.md` |
| 建置即安裝（使用者自己建出可用的東西，例如可開機映像） | 建出可用產物的最短步驟 | — |
| 尚未發佈 | 寫明「目前沒有可用版本」，以及現在能怎麼試（例如「從原始碼執行，見 `docs/DEVELOPER.md`」） | — |

- 部署型與建置即安裝**可**在本章寫建置或部署指令，因為那就是使用者取得它的方式；**為了修改程式**而做的環境建置仍只寫在 `DEVELOPER.md`。
- 尚未發佈的專案**禁止**寫「未來正式版本的預定安裝方式」——只寫現況。
- 同一份 README 只能套一種情形；兩種都有（例如同時提供下載版與自架版）時，各開一個 H3。

### 4.11 授權

- 授權全文**必須**放在根目錄，檔名**必須**為 `LICENSE`（無副檔名）。
- `## 授權` **必須**寫出授權名稱並連結 `LICENSE`。
- 沒有特別理由時，依儲存庫的可見性採用預設授權：

| 可見性 | 預設授權 |
| :--- | :--- |
| 私有 | PolyForm Noncommercial License 1.0.0 |
| 公開 | GNU General Public License v3.0（GPL-3.0） |

- 這只是**預設**：專案**可**改用其他授權，並在 `## 授權` 寫明。
- 儲存庫在公開與私有之間切換時，**不一定**要換授權；要換時，新版起適用新授權，已發佈的版本維持原授權。
- `LICENSE` **必須**是官方全文，**禁止**自行改寫條文。

## 5. 範例與註解慣例

### 5.1 佔位符

需要使用者替換的部分**必須**用角括號包住，內容為繁中描述：

```text
<專案代號小寫>_v<版本號>_setup.exe
```

**禁止**用 `xxx`、`your-app`、`TODO` 之類的佔位方式。

### 5.2 範例的可執行性

- 指令範例**必須**能原樣執行（佔位符除外），**禁止**貼未驗證過的指令。
- 範例中的版本號一律用 `v1.0.0`，路徑一律用相對路徑。
- 需要示範虛構專案時，一律用 `MYAPP`。**禁止**用真實的其他專案名稱。

### 5.3 註解

- 程式碼區塊內用該語言的註解符號，Markdown 內用 `<!-- -->`。
- 註解一律繁中，用來說明**為什麼**，不重複指令本身在做什麼。

### 5.4 驗證 About 與 README 一致

§4.7 要求逐字相同。**沒有驗證手段的規則會漂**——尤其中文的全形半形、空格差異用眼睛看不出來。發佈前跑這一段（擇一）：

```bash
repo='<擁有者>/<儲存庫>'
about=$(gh repo view "$repo" --json description --jq .description)
line=$(grep -m1 '^> ' README.md | sed 's/^> //')
echo "About  : $about"
echo "README : $line"
[ "$about" = "$line" ] && echo "相同   : True" || echo "相同   : False"
```

```powershell
$repo   = '<擁有者>/<儲存庫>'
$readme = 'README.md'

$about = (gh repo view $repo --json description | ConvertFrom-Json).description
$line  = ((Get-Content $readme -Encoding UTF8 |
           Select-String -Pattern '^> ' | Select-Object -First 1).Line -replace '^> ', '').Trim()

"About  : $about"
"README : $line"
"相同   : $($about -eq $line)"
```

前提是定位句以 `> ` 引述行的形式緊接在 H1 之後——這也是 [範本](templates/README.template.md) 的寫法。

## 6. 禁止事項

| 禁止寫進 README | 應該寫在哪 |
| :--- | :--- |
| 為了修改程式的環境建置、相依套件安裝 | `DEVELOPER.md` |
| 建置、打包、測試指令（部署型與建置即安裝的取得步驟除外，見 §4.10） | `DEVELOPER.md` |
| 依主機而異的部署細節 | `DEPLOY.md` |
| 目錄結構、架構說明、設計決策 | `DEVELOPER.md` |
| 分支策略、commit 格式 | `DEVELOPER.md` |
| 逐版變更紀錄 | `CHANGELOG.md` |
| 發佈流程、產物命名 | `RELEASE_RULES.md` |

另**禁止**：

- 本機絕對路徑（`D:\...`、`/home/...`）、個人帳號、金鑰、憑證密碼。
- `TODO`、`待補`、`施工中` —— 沒寫好就不要留標題。
- 尚未發佈的功能與預定的安裝方式。README 描述的**必須**是使用者現在拿得到的版本。
- 與 `CHANGELOG.md` 重複的完整更新清單。

About 另**禁止**：

- 簡介與 README 的一句話定位不同（含全形半形、空格的差異）。
- 定位句含 Markdown 語法——它要能直接貼進 About。
- 簡介寫技術棧或無法驗證的形容。
- topics 為空，或同系列的專案彼此沒有共用的 topic。
- 網站填儲存庫自己的網址或 Releases 頁面。

## 7. 檢查清單

發佈前逐項確認：

- [ ] 檔案在根目錄，UTF-8 無 BOM、LF、檔尾一個換行
- [ ] 七個必要章節齊全、順序正確、標題逐字相符
- [ ] 只有一個 H1，且是顯示名「《專案名稱》(專案代號)」
- [ ] 第一段就講清楚「這是什麼、給誰用」
- [ ] 「取得與安裝」照 §4.10 的情形寫；部署細節在 `docs/DEPLOY.md`；尚未發佈的只寫現況
- [ ] `## 授權` 寫了授權名稱並連結根目錄的 `LICENSE`
- [ ] 「快速開始」的步驟自己實際跑過一遍
- [ ] 所有指令區塊標了語言、沒有提示符、可原樣複製
- [ ] 所有連結可點、圖片顯示正常、圖片有替代文字
- [ ] 沒有任何建置 / 測試 / 架構內容（§6）
- [ ] 沒有絕對路徑、金鑰、個人資訊
- [ ] 沒有 TODO 與未發佈功能
- [ ] 描述的功能與目前最新發佈版本一致
- [ ] 末尾的 `## 開發者` 連結 `docs/DEVELOPER.md` 與 `docs/CHANGELOG.md`

About（不進版控，改了不會有人 review，所以每次發佈都要看一眼）：

- [ ] 簡介與 README 的一句話定位**逐字相同**（用 §5.4 的指令驗，不要用眼睛）
- [ ] 定位句是純文字，沒有 Markdown 語法
- [ ] 簡介 100 字以內，沒有技術棧、沒有無法驗證的形容
- [ ] topics 涵蓋領域、專案型態、主要技術三個面向
- [ ] 同系列的專案共用至少一個 topic
- [ ] 網站欄位：有線上版才填，否則留空；沒有填成儲存庫自己的網址
